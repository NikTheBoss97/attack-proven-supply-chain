# ADR-0007: How the attack suite works

- Status: accepted
- Date: 2026-11-05

## Context

The project's main claim is that each control stops a real attack, and four runs
prove it: the attack succeeds with the control off, it is stopped with the control
on, its nearest variant is stopped too, and normal use still works. ADR-0002 left
open how a weakness can exist for the control-off run without being left open in what
ships. The suite also needs a harness, a way to keep one control from deciding
another's test, and a way to publish results without giving CI write access.

## Options

How an application control gets turned off. Platform controls, such as admission and
network policies, are simply not installed for that run.

| Option | Why not |
|---|---|
| **A patch per control, applied to a temporary copy of the code** | Chosen. `attacks/<id>/control-off.patch` removes the control, and the suite builds a throwaway image from the result. What ships contains no weak code and no off switch. The patch shows exactly which lines are the control, and `git apply` fails the whole patch if the code has moved, so an attack cannot go stale silently. |
| A runtime switch in the service | It needs only one image and runs quickly, but the shipped image could disable its own security, and one bad setting reopens the hole. |
| An old commit or a vulnerable branch | It tests history rather than today's code, and a branch drifts. |

The harness:

| Option | Why not |
|---|---|
| **pytest** | Chosen. It is already Python, its fixtures handle cluster setup and teardown, and a reviewer can read it. It needs a small plugin to write the results file. |
| Shell scripts | They are the closest to what an attacker would type, but assertions and structured results get brittle. |
| A ready-made tool such as Stratus Red Team | It has Kubernetes techniques, but its stated purpose is validating detections. Nothing on its page shows it asserting that a given control stopped an attack for the right reason. |

What runs together:

| Option | Why not |
|---|---|
| **One control at a time, plus one normal-use test with everything on** | Chosen. Each run toggles only the control under test, so a result can be traced to that control. |
| Every control on in every run | It is closer to production, but it cannot tell which control stopped an attack. An unsigned control-off image would also be blocked by admission, for the wrong reason. |

The results table in the README:

| Option | Why not |
|---|---|
| **Generated locally and committed, then regenerated by CI, which fails on any difference** | Chosen. CI keeps its read-only token, and it still proves the table matches a real run. |
| Committed by CI | It needs a write token, which breaks the project's read-only rule, and a commit straight to `main` would skip the pull request rule. |

## Decision

Each attack is a directory in `attacks/`. A shared base class requires all four runs:

| Run | Control | What it tries | Must report |
|---|---|---|---|
| Control off | Off | The attack and its variant | `succeeded` |
| Control on | On | The attack | `blocked` or `detected`, with the expected reason |
| Variant | On | The nearest bypass | `blocked` or `detected`, with the expected reason |
| Legitimate | On | Normal use | It works |

- The control-off run also tries the variant, because a variant that could never work
  would pass and prove nothing.
- If setup breaks, the run reports `error`, never `blocked`, and the suite fails. A
  webhook that was not ready cannot pass as a stopped attack.
- The suite creates its own `kind` cluster with a unique name and its own kubeconfig
  file, so it cannot touch any other cluster the machine points to.
- Control-off images are loaded only into that cluster, and are never pushed or
  signed.
- Each attack names its threat IDs and its control page, and the suite fails if either
  is missing.

The first attack, in Phase 1, is broken object-level authorization, because it needs
only the service and a cluster. Bob reads Alice's bookmark by its ID. The control is
the ownership check. The expected reason is a 404 with `bookmark_not_found`, after
first proving that Alice's bookmark exists. The variant is Bob deleting it, because a
check written only for reads would let that through. The legitimate run is Alice
reading and deleting her own bookmark.

## Consequences

- Patches need upkeep when the code moves, and each application attack adds an image
  build.
- How long a full run takes is unknown until it is measured in Phase 1.
- Any change to an attack's result means regenerating the table locally, so the suite
  has to be runnable outside CI.
- Toggling one control at a time does not show how controls interact, beyond the one
  normal-use test.
- The link to mutation testing, breaking the code on purpose to see whether a test
  notices, is this project's analogy. The papers behind it do not make claims about
  security controls.
